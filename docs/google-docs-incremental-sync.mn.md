# Google Docs-оор өөрчлөлтийн хэсгийг sync хийх

## Яаж ажилладаг вэ

Memory-ийн зөвшөөрөгдсөн segment бүрийг Google Docs-ийн нэг буюу хэд хэдэн баримтад хадгална. Нэг баримт 1,000,000 UTF-16 нэгжээс хэтэрвэл хэсэглэнэ. NotebookLM-д тэр баримтыг Drive эх сурвалж болгон холбоно. Бүх Markdown-ийг дахин upload хийхийн оронд Docs баримт доторх нэмэх, солих, устгах үйлдлийг илгээнэ.

Анхны шилжилтэд өмнө нь нийтэлсэн, зөвшөөрөлтэй segment-үүдийг Docs руу **нэг удаа бүтнээр нь** бичнэ. Дараагийн өөрчлөлтүүдэд мөрийн түвшний Myers diff хэрэглэж зөвхөн өөрчлөгдсөн хэсгийн UTF-16 байрлал, шинэ текстийг илгээнэ. Алслагдсан хоёр өөрчлөлтийн дундах хэвээр үлдсэн текст request body-д орохгүй. Diff ажлын хязгаараас хэтэрсэн их хэмжээний дахин бичилтэд нэг яг таг patch руу fallback хийж болох тул тэр үед илүү их текст дамжина.

SQLite journal нь өмнөх текст, хүлээгдэж буй transaction-ийг илгээхээс өмнө хадгална. Хариу тасарвал дахин илгээхийн өмнө баримтын fingerprint-ийг шалгаж өөрчлөлт аль хэдийн хадгалагдсан эсэхийг тогтооно. Өмнөх NotebookLM source-уудыг шинэ Docs source-ууд бүрэн index хийгдэж бэлэн болтол устгахгүй. Шинэчилж байгаа segment-ийг retrieval-д түр гаргахгүй.

Хэсэг бүрийн эхэнд агуулгатай нь холбоотой богино шалгах код хадгална. NotebookLM тухайн кодыг зөв эх сурвалжаас эшилж чадвал Memory тэр хувилбарыг нийтлэгдсэн гэж бүртгэнэ. Ийм шалгалтад нэг жижиг асуулт хэрэглэнэ. Сегментийн анхны нийтлэлд NotebookLM асуултад алдаа буцаавал индексжүүлсэн эх сурвалжийн текстийг уншиж, яг тэр кодыг тулгана. Том initial upload-ийг хэд хэдэн баталгаажуулсан хүсэлт болгон хуваана.

## API-ийн чухал ялгаа

Энэ нь Google Docs-ийн **нийтийн албан ёсны REST API биш**. Brave-д нэвтэрсэн хэрэглэгчийн Docs editor-ийн дотоод save endpoint-ийг Playwriter-аар ашигладаг. Google editor-ийн протокол өөрчлөгдвөл sync эвдэрч болно. Албан ёсны API шиг тогтвортой байдал гэж үзэж болохгүй. Brave болон NotebookLM ижил Google account-д хандах эрхтэй байх шаардлагатай.

## Идэвхжүүлэх дараалал

`mem` дотор **Холболт → Docs холбох** эсвэл `/docs-connect` ажиллуулна. Brave-д NotebookLM-ийн баримтуудад хандах Google аккаунтаараа нэвтэрсэн байна. Docs-ийн хадгалалт Brave-ийн сессийг ашигладаг. `mem`-ийн **Нэвтрэх** товч NotebookLM-ийн холболтыг шинэчилдэг. **Урсгал** дээр Docs-ийн төлөв, `/sync-all`-ийн ажлын үр дүн дээр Docs хадгалалтын байт харагдана.

1. Brave profile дээрээ Google Docs-д нэвтэрсэн эсэхийг шалга.
2. Ижил SQLite archive болон notebook ID тохируулагдсан эсэхийг шалга.
3. `docs-web-enable` нь publication тохиргоог шилжүүлж, нийтлэгдсэн segment-ийн revision-ийг шинэчилнэ. Энэ команд өөрөө upload хийхгүй.
4. Дараагийн `ai-memory sync` өмнө нийтэлсэн зөвшөөрөгдсөн segment-үүдийг Docs руу анх удаа бүтнээр нь шилжүүлнэ. Эхлээд archive backup авч, NotebookLM source quota-г шалга.

Жишээ:

```bash
.venv/bin/ai-memory --db /absolute/path/archive.sqlite docs-web-enable
.venv/bin/ai-memory --db /absolute/path/archive.sqlite sync
.venv/bin/ai-memory --db /absolute/path/archive.sqlite status
```

`docs-web-enable` ажиллаж буй Brave session-ийг дахин ашиглана. Анх холбоход эсвэл хадгалсан session ажиллахгүй бол шинээр үүсгэнэ. `--session ID` өгч бэлдсэн session ашиглаж болно. Нэвтрэлтгүй бол тохиргоог өөрчлөхөөс өмнө `docs_web_auth_required` алдаа өгнө.

## Хэмжилтийг зөв ойлгох

`sync` үр дүн дэх `docs_web_write_payload_bytes` нь хариугаар баталгаажсан Docs save хүсэлтүүдийн POST body-ийн байт. Тасарсан хүсэлтийн байт энэ хэмжилтэд дутуу орж болно. Browser ачаалалт, нэвтрэлт, серверийн хариу, эргэлзээтэй бичилтийн үед Docs редакторын хадгалсан загварыг дахин унших, NotebookLM-ийн хүсэлтүүд тусдаа дата хэрэглэнэ. Бодит туршилтаар 1,000 үгтэй Docs дээр 10 үг нэмэх POST body **282 байт** болсон. Google Docs-ийн текст хүлээсэн хувилбартай таарч, NotebookLM шинэ үгийг хариултдаа ашиглан өмнөхтэй адил эх сурвалжийг эшилсэн. Нэг үг солих, өөр байрлалаас текст устгах хоёр үйлдлийг **354 байт** POST body-оор хадгалсан. Эхний бүтэн шилжилтэд архивын агуулгыг нэг удаа Docs руу бичнэ.

Үндсэн архивын туршилтаар 516 байтын бодит мессежийг 132,167 байтын агуулгатай Docs-д нэмэх хадгалах хүсэлт **1,401 байт** болсон. Хариу тасарсны дараа хадгалсан хувилбарыг тулгаж, тухайн хүсэлтийг сэргээн баталгаажуулсан. Мессеж баримтад нэг удаа орсныг шалгасан. `memory_ask` мессежийн 3-р асуултыг эш татаж, `SEG-010 part 1` эх сурвалжийг заасан.

`status` дахь `google_docs` хэсэг:

- `documents`: үүссэн Docs баримтын тоо
- `written_parts`: Docs-д бичигдсэн хэсэг
- `indexed_parts`: NotebookLM-д index хийгдсэн хэсэг
- `updating_segments`: одоо шилжүүлж буй segment
- `unconfirmed_legacy_uploads`: хуучин Markdown upload-ийн баталгаажаагүй ажлууд

## Recovery ба хязгаарлалт

- Memory-ийн үүсгэсэн Docs баримтыг Memory өөрөө шинэчилнэ. Хүйтэн session сэргээхэд өмнөх hash зөрвөл `docs_web_conflict` гэж зогсоно. Сервер зэрэг засварын улмаас өөр revision баталбал Memory түүнийг нийтлэхгүй, тусад нь шалгана.
- POST-ийн хариу тасарвал transaction journal болон fingerprint-ээр давхар insert хийхээс сэргийлнэ.
- Шинэ Docs үүсмэгц Drive ID-г архивт хадгална. Нэр солих хүсэлтийн хариуг хүлээгээд, Google-ээс тухайн ID-тай баримтыг шинээр нээж хадгалсан нэрийг тулгана. Нэр батлагдаагүй бол дараагийн оролдлого тэр ID-аар үргэлжилнэ. Нэр батлагдсаны дараа агуулгыг бичиж, NotebookLM-д холбоно.
- Баримт үүсгэх эсвэл NotebookLM-д холбоход үр дүн тодорхойгүй бол duplicate үүсгэхийн оронд uncertain төлөвт үлдээнэ. Автоматаар таамаглан устгахгүй; гараар шалгах шаардлагатай байж болно.
- Өдөр тутмын sync-д NotebookLM шалгах асуултад алдаа буцаавал баталгаажуулалтыг дараагийн оролдлогоор үргэлжлүүлнэ. Хадгалсан өөрчлөлтийг дахин илгээх шаардлагагүй.
- Google Docs-ийн private endpoint, Playwriter/Brave session-ийн нийцтэй байдал болон NotebookLM-ийн live indexing нь offline тестээр бүрэн батлагдахгүй. Жинхэнэ archive дээр шилжүүлэхээс өмнө тусдаа synthetic archive болон хоосон demo notebook дээр турш.
- Сегмент багасвал хэрэггүй болсон NotebookLM холбоосыг шинэ хувилбар баталгаажсаны дараа устгана. Тухайн хувийн Drive баримтыг дахин ашиглахаар хадгална.
