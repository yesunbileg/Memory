# Google Docs-оор өөрчлөлтийн хэсгийг sync хийх

## Яаж ажилладаг вэ

SQLite архив нь эх хувь. Memory-ийн удирддаг Docs баримтад санамсаргүй гараар засвар орвол дараагийн sync зөвшөөрөгдсөн, нууцыг маскалсан архиваас зөрсөн текстийг сэргээнэ. Сэргээсэн хэсгийг NotebookLM дахин индексэлж баталгаажуулна. Өөрчлөлтгүй баримтыг текстийн экспортоор шалгахад хадгалах хүсэлт гарахгүй.

Memory идэвхтэй чатуудын багцыг Google Docs-д хадгална. Нэг баримт 1,000,000 UTF-16 нэгжээс хэтэрвэл хэсэглэж, NotebookLM-д Drive эх болгон холбоно. Docs доторх нэмэх, солих, устгах үйлдлийг хэсэгчлэн илгээнэ. `ai-memory sync --archive-cold` идэвхжсэн архивт 30 хоног шинэчлэгдээгүй чатуудыг 400,000 үг хүртэлх Markdown эхэд нэгтгэнэ. Орлуулах бүх эх бэлэн болсны дараа хуучин NotebookLM холбоосуудыг цэвэрлэнэ.

Анхны шилжилтэд өмнө нь нийтэлсэн, зөвшөөрөлтэй segment-үүдийг Docs руу **нэг удаа бүтнээр нь** бичнэ. Дараагийн өөрчлөлтүүдэд мөрийн түвшний Myers diff хэрэглэж зөвхөн өөрчлөгдсөн хэсгийн UTF-16 байрлал, шинэ текстийг илгээнэ. Алслагдсан хоёр өөрчлөлтийн дундах хэвээр үлдсэн текст request body-д орохгүй. Diff ажлын хязгаараас хэтэрсэн их хэмжээний дахин бичилтэд нэг яг таг patch руу fallback хийж болох тул тэр үед илүү их текст дамжина.

SQLite journal нь өмнөх текст, хүлээгдэж буй transaction-ийг илгээхээс өмнө хадгална. Хариу тасарвал дахин илгээхийн өмнө баримтын fingerprint-ийг шалгаж өөрчлөлт аль хэдийн хадгалагдсан эсэхийг тогтооно. Өмнөх NotebookLM source-уудыг шинэ Docs source-ууд бүрэн index хийгдэж бэлэн болтол устгахгүй. Шинэчилж байгаа segment-ийг retrieval-д түр гаргахгүй.

Хэсэг бүрийн эхэнд агуулгатай нь холбоотой богино шалгах код хадгална. Memory шинэчлэгдсэн хэсгийн индексэлсэн текстийг NotebookLM-ээс уншиж, кодыг яг тулгасны дараа тухайн хувилбарыг нийтлэгдсэн гэж бүртгэнэ. Шалгалт чатад асуулт үүсгэхгүй. Том initial upload-ийг хэд хэдэн баталгаажуулсан хүсэлт болгон хуваана.

## API-ийн чухал ялгаа

Memory архивын хадгалсан Google нэвтрэлтээр Docs-ийн дотоод save endpoint-ийг ашиглана. Docs редактор нь синк бүрд түр, цонхгүй Brave процесс дотор ажиллана. Хэрэглэгчийн Brave цонх, таб эсвэл тусдаа нэвтрэлт шаардахгүй. Google редакторын протокол өөрчлөгдвөл синк эвдэрч болно.

## Идэвхжүүлэх дараалал

`mem` дотор **Холболт → Docs холбох** эсвэл `/docs-connect` ажиллуулна. Энэ үйлдэл архивын Google нэвтрэлтийг ашиглана. Хугацаа нь дууссан бол **Нэвтрэх** товч эсвэл `/login` командаар шинэчилнэ. **Урсгал** дээр Docs-ийн төлөв, `/sync-all`-ийн ажлын үр дүн дээр Docs хадгалалтын байт харагдана.

1. Memory-д NotebookLM-ээр ашиглаж буй Google нэвтрэлт байгаа эсэхийг шалга.
2. Ижил SQLite archive болон notebook ID тохируулагдсан эсэхийг шалга.
3. `docs-web-enable` нь publication тохиргоог шилжүүлж, нийтлэгдсэн segment-ийн revision-ийг шинэчилнэ. Энэ команд өөрөө upload хийхгүй.
4. Дараагийн `ai-memory sync` өмнө нийтэлсэн зөвшөөрөгдсөн segment-үүдийг Docs руу анх удаа бүтнээр нь шилжүүлнэ. Эхлээд archive backup авч, NotebookLM source quota-г шалга.

Жишээ:

```bash
.venv/bin/ai-memory --db /absolute/path/archive.sqlite docs-web-enable
.venv/bin/ai-memory --db /absolute/path/archive.sqlite sync
.venv/bin/ai-memory --db /absolute/path/archive.sqlite status
```

`docs-web-enable` нь шинэ тохиргоог хадгалахын өмнө цонхгүй горимоор холболтыг баталгаажуулна. Өмнө холбосон архив дараагийн синкээс арын горимыг ашиглана. Нэвтрэлтгүй бол `docs_web_auth_required` гарна. Суулгахдаа Brave болон Playwright хэрэгтэй. Wheel-ээр суулгасан бол `docs` нэмэлтийг суулгана.

## Хэмжилтийг зөв ойлгох

`sync` үр дүн дэх `docs_web_write_payload_bytes` нь хариугаар баталгаажсан Docs save хүсэлтүүдийн POST body-ийн байт. Тасарсан хүсэлтийн байт энэ хэмжилтэд дутуу орж болно. Browser ачаалалт, нэвтрэлт, серверийн хариу, эргэлзээтэй бичилтийн үед Docs редакторын хадгалсан загварыг дахин унших, NotebookLM-ийн хүсэлтүүд тусдаа дата хэрэглэнэ. Цонхгүй горимын хэмжилтийг тусгаарласан туршилтын өгөгдлөөр дахин баталгаажуулна.

`status` дахь `google_docs` хэсэг:

- `documents`: үүссэн Docs баримтын тоо
- `written_parts`: Docs-д бичигдсэн хэсэг
- `indexed_parts`: NotebookLM-д index хийгдсэн хэсэг
- `updating_segments`: одоо шилжүүлж буй segment
- `unconfirmed_legacy_uploads`: хуучин Markdown upload-ийн баталгаажаагүй ажлууд

## Recovery ба хязгаарлалт

Docs-ийн hash/revision-ийг NotebookLM-д холбоно/индексжүүлэхээс өмнө болон бүх part индексжсэний дараа бие даан дахин тулгана. Шинэ source-ийн Drive ID-г inventory-оор баталгаажуулна. Зөрчилтэй/transform хийсэн ACK-г нийтлэхгүй. Энэ нь атомик server-side CAS биш; зэрэг засварлах эрсдэл бүрэн арилгагдаагүй. Дахин унших сүлжээний дата өсөх боломжтой.


- Сэргээх үед Docs-д өөр хувилбар хадгалагдвал Memory дахин шалгаж, дараагийн sync-ээр үргэлжлүүлнэ. `/auto off` үед сэргээх ажлыг гараар эхлүүлсэн sync гүйцэтгэнэ.
- POST-ийн хариу тасарвал transaction journal болон fingerprint-ээр давхар insert хийхээс сэргийлнэ.
- Шинэ Docs үүсмэгц Drive ID-г архивт хадгална. Нэр солих хүсэлтийн хариуг хүлээгээд, Google-ээс тухайн ID-тай баримтыг шинээр нээж хадгалсан нэрийг тулгана. Нэр батлагдаагүй бол дараагийн оролдлого тэр ID-аар үргэлжилнэ. Нэр батлагдсаны дараа агуулгыг бичиж, NotebookLM-д холбоно.
- Баримт үүсгэх эсвэл NotebookLM-д холбоход үр дүн тодорхойгүй бол duplicate үүсгэхийн оронд uncertain төлөвт үлдээнэ. Автоматаар таамаглан устгахгүй; гараар шалгах шаардлагатай байж болно.
- NotebookLM шинэ шалгах кодыг хараахан индексэлж амжаагүй бол баталгаажуулалт дараагийн оролдлогоор үргэлжилнэ. Хадгалсан өөрчлөлтийг дахин илгээх шаардлагагүй.
- Google Docs-ийн private endpoint, цонхгүй Brave-ийн нийцтэй байдал болон NotebookLM-ийн live indexing-ийг туршилтын архив, хоосон demo notebook дээр шалгана.
- Сегмент багасвал хэрэггүй болсон NotebookLM холбоосыг шинэ хувилбар баталгаажсаны дараа устгана. Тухайн хувийн Drive баримтыг дахин ашиглахаар хадгална.

Одоогийн шалгалтыг [локал тестийн заавраар](local-testing.mn.md) ажиллуулна.

Audit болон benchmark нь үйлдвэрлэлийн синктэй ижил цонхгүй Brave worker ашиглана. Тусгаарласан хоосон notebook, шинэ output хавтас болон тохирох Google нэвтрэлтийн файлыг `--storage PATH`-аар заана. Тайланд зөвхөн хэмжилт, hash, төлөв хадгална.
